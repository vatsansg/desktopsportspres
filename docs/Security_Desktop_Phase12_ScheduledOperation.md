# Security Checklist — Desktop Phase 12: Scheduled Operation

Release/hand-off: Phase 12 — Scheduled Operation (Steps 12.1, 12.2). Date: 23/09/26. Application: Desktop.
Status values: **Pass**, **Fail**, **N/A at this stage**, **Accepted risk** (BRD-accepted items and any the owner explicitly signs off).

**Theme of this phase:** for the first time, this application stores and uses a real Windows account's credentials to run itself unattended, and introduces a second process (a headless scheduled run) that touches the same database and the same mapped LED folders as the interactive app. Three things must stay true: (1) the Windows account password is never stored, logged, or echoed anywhere by this application — Windows' own credential store is the only place it lives; (2) the interactive app and a scheduled run can never collide on the same data folder; (3) the headless entry point can never load any GUI toolkit, so it genuinely works with nobody signed in.

## B. Identity & access (Desktop Application)

| # | Item | Status | Notes |
|---|---|---|---|
| B1 | Storage Account access key not committed and protected | **Pass (unchanged)** | Not touched this phase. |
| B2 | Accepted-risk plain-text admin credential has not expanded in scope | **Pass (unchanged)** | `admin_*` keys untouched; `settings.py`'s scope guard still refuses any key it does not own. |
| B3 (added) | **The Windows account password is never stored by this application** | **Pass** | It exists only as a Flask request-form value for the single request that calls `scheduler.register()`, and as a Python local variable inside `register()`/`_invoke()` for the single `schtasks` call — never written to SQLite, never logged, never placed in a session, never returned in a response. `services/settings.py`'s `ScheduleSettings`/`save_schedule` do not have a password field at all - the password cannot reach that module even by mistake, since the view layer never passes it there. |
| B4 (added) | **A second, genuinely unattended execution path is behind the same access the interactive app already requires** | **Pass** | `Settings -> Scheduling` (GET/POST) requires `login_required` + CSRF, same as every other settings page. The headless run itself needs no HTTP login (it is not a web request at all - it is what Windows Task Scheduler launches directly), but it can only act on data the operator already configured while signed in to the app; it cannot change settings, cannot register itself, and cannot be reached over the loopback HTTP server (it never starts one). |

## D. Data protection

| # | Item | Status | Notes |
|---|---|---|---|
| D1 | **The Windows account password never appears in any log, exception, or oplog message** | **Pass** | `scheduler.SchedulerError`'s message is always one of a small set of fixed sentences (see F below); `schtasks`' own stdout/stderr is captured but never interpolated into anything raised, logged, or shown. Verified: a failing registration's exception text and the operator-facing page error both exclude the password and schtasks' raw output, even though the fake test transport deliberately returns password-adjacent-looking text in `stderr` to prove this. |
| D2 | **The account name is not treated as a secret (correctly)** | **Pass** | A Windows account name is not sensitive on its own (the equivalent of a username) - shown back on the settings page, validated only for shape (and refused if it looks key-shaped, in case a password was pasted into the wrong box by mistake) like every other non-secret settings field. |
| D3 (added) | **The database and the real Task Scheduler entry can never silently disagree** | **Pass (after a review fix)** | `scheduler.register()`/`unregister()` is called *before* `save_schedule()` persists anything; a failure refuses the whole save. An earlier version left one gap: if registration succeeded but the *database write itself* then failed (a genuine SQLite error), Windows could be left registered while the database disagreed - reproduced by the review and fixed with a best-effort compensating `unregister()` on that specific failure path (see S-70). Both the enable and disable paths are now guarded identically (S-71 - the disable path's `unregister()` was previously unguarded). |
| D4 (added) | **Cross-process safety: the interactive app and a scheduled run can never touch the database or a mapped LED folder at the same time** | **Pass** | `services/singleinstance.py`'s OS-level advisory lock (`msvcrt.locking`) is taken by both entry points before any database access; a second acquisition attempt fails immediately (never blocks, never silently proceeds), and the lock is released automatically by the operating system the instant the process exits - including a crash - so there is no stale-lock state requiring cleanup or manual recovery, unlike a PID file. Reviewed and confirmed no TOCTOU gap and correct release-on-exception behaviour. |
| D5 (added) | **The headless entry point cannot load a GUI toolkit even by accident** | **Pass** | `scheduled_run.py` has no import of `webview`, Flask, or anything from `ledsync.web`, verified by a real subprocess test (mirroring the equivalent guarantee `ledsync.main` already had) - this matters because a GUI/COM toolkit can behave unpredictably or fail outright with no desktop session present (the "nobody logged in" case Addendum A 39.6 requires). Reviewed: the whole transitive import chain from `scheduled_run.py` (through `downloads.py`, `storage.py`, etc.) was checked and contains no win32/COM/registry/desktop-session dependency anywhere. |
| D6 (added) | **The scheduled run finds the venue's real data regardless of which Windows account Task Scheduler runs it as** | **Pass (after a review fix, S-72)** | An earlier version relied on `config.load()`'s usual `%LOCALAPPDATA%` resolution inside the scheduled process itself - scoped to whichever account actually executes the Task, not necessarily the account that configured the schedule. Since Addendum A 39.6's whole point is to let the schedule run as a dedicated account different from the interactive operator, this was a real, silent-failure-shaped gap (see S-72 below). Fixed: the registering session's own `cfg.data_dir` is now baked into the Task's `--data-dir` argument at registration time, so the scheduled process is told explicitly where the data is rather than guessing from its own account context. |

## E. Application security

| # | Item | Status | Notes |
|---|---|---|---|
| E1 | Input validation / injection | **Pass** | The Windows account field is validated (shape/length/secret-shaped-value checks); the Task Scheduler XML is built with every variable field (username, working directory, interpreter path) passed through `xml.sax.saxutils.escape` before insertion, so a crafted account name cannot break out of its XML element or inject a second trigger/action. `schtasks` is invoked via `subprocess.run` with an argument LIST (never a shell string), so there is no shell-injection surface regardless of what the account name or password contain. |
| E2 | Output encoding / XSS | **Pass** | Jinja auto-escaping for the new fields, matching every other settings field. |
| E5 | Errors do not leak internals | **Pass** | Every `scheduler.SchedulerError` is one of a small set of fixed, plain messages; `schtasks`' own output is captured but never shown to the operator or written to any log. |
| E12 (added) | **Background/unattended job safety** | **Pass** | `scheduled_run.py` catches per-event exceptions around each `downloads.run_job` call so one event's failure cannot stop the loop, and the outer `main()` catches everything else so a genuinely unexpected error still exits cleanly (logged to the diagnostic log) rather than leaving Task Scheduler to report a crash with no explanation in the application's own logs. |
| E15 (added) | **No shell injection via the generated Task Scheduler command** | **Pass** | The Task's `<Command>`/`<Arguments>` are the real Python interpreter path (`sys.executable`, not operator-controlled) and a fixed literal (`-m ledsync.scheduled_run`) - nothing about the schedule (days, time, account name) is concatenated into the command line the Task actually executes. |

## Findings

| ID | Severity | Finding | Action |
|---|---|---|---|
| S-72 | **High → Closed** | (Review, first pass: rejected on this finding) The scheduled process resolved its data folder via the normal `%LOCALAPPDATA%` path, which is scoped to whichever Windows account actually runs the Task - not necessarily the account that registered it. Addendum A 39.6 exists precisely so the schedule can run as a dedicated account different from the interactively signed-in operator; in that entirely reasonable configuration, the scheduled run would silently find an *empty* data folder, see no registered events, and log `Scheduled Run` / `Success` ("No events are registered; nothing to do") on every single run, forever - with nothing in the application's own logs to indicate anything was wrong. | Fixed: the registering session's own real `cfg.data_dir` is now baked into the Task's `--data-dir` argument at registration time (`scheduler.py`'s `_task_xml`/`register()`); `scheduled_run.py` accepts `--data-dir` and, when given, uses it directly instead of `config.load()`'s account-scoped default. New regression tests (`test_data_dir_argument_is_authoritative_regardless_of_the_running_account`, `test_register_bakes_the_registering_sessions_data_dir_into_the_task`). |
| S-70 | **Medium → Closed** | (Review) If `scheduler.register()` succeeded but the subsequent `cs.save_schedule()` database write then failed (a genuine SQLite error, not a validation problem), the real Task Scheduler entry was left registered while the database still held the old/no schedule - contradicting D3's "can never disagree" claim, which held only for the account/password-rejection case. | Fixed: a database-save failure occurring after a successful registration now makes a best-effort compensating `unregister()` call before the error is shown, restoring the "off" state on both sides. New regression test (`test_a_database_failure_after_a_successful_registration_rolls_back_the_task`). |
| S-71 | **Low → Closed** | (Review) The disable path (`scheduler.unregister()`) was called unguarded in the view, unlike the enable path's `register()` call which was already wrapped in `try/except SchedulerError`. A transient `schtasks` failure there (e.g. hitting the 30s timeout) would have surfaced as an uncaught exception → Flask's generic 500 page, with no `record_rejection` audit row - unlike every other settings-save failure in this application. | Fixed: both the enable and disable paths now go through the same `try/except scheduler.SchedulerError -> refused(...)` handling. New regression test (`test_a_failed_unregister_is_refused_and_logged_not_silently_500d`). |
| — | Info, accepted | (Review note) The Windows account password is briefly visible on the `schtasks.exe` child process's own command line (via `/RP`) for that process's short lifetime, to anything with sufficient privilege to enumerate process command lines (Task Manager, WMI). Inherent to `schtasks.exe`'s own interface (there is no stdin alternative) and not avoidable by this code - already implicit in the module's own docstring ("exactly as if an administrator had typed it into the Task Scheduler UI by hand"). | Accepted; noted explicitly here for completeness. |
| S-73 (live) | **High → Closed** | (Live validation, 23/09/26) `email_notify.py`'s `_send()` caught every exception from the Azure SDK call and re-raised a mapped `NotifyError` via `raise _map_error(exc) from None`, with no `log.exception` call anywhere on that path - the real exception and its traceback were permanently lost, not just redacted. This is a diagnosability gap, not a secrets-exposure one, but it is what made Phase 11's F-76/S-69 unreproducible for two phases running: without it, the actual cause (a truncated, invalid access key - see S-75) could never have been found. | Fixed: `_send()` now calls `log.exception(...)` before re-raising, to the same diagnostic log every other unexpected error already goes to (never to the oplog or the page - those still only ever get the fixed, mapped message, unchanged). |
| S-74 (live) | **Medium → Closed** | (Live validation, 23/09/26) `settings.py`'s `validate_email_connection()` checked only the overall string length (20-2000 characters); it never parsed the connection string or validated the access key's base64 form. A malformed value (see S-75) was silently accepted and saved, and only failed - opaquely - the next time a real send was attempted, by which point the operator has no way to know *why* without the S-73 fix above. | Fixed: now parses `endpoint=...;accesskey=...` (mirroring `email_notify._parse_connection_string`, kept as a separate small implementation to avoid a circular import) and validates the key with `base64.b64decode(..., validate=True)`, refusing an invalid one immediately with a clear, non-secret-echoing message. New test: `test_a_connection_string_with_incorrectly_padded_access_key_is_refused_at_save_time`. |
| S-75 (live) | **Medium → Closed** | (Live validation, 23/09/26) `settings_email.html`'s connection-string field used the shared `password_field` macro's default `maxlength="128"` (correct for the Cloud Storage access key alone, 88 characters, but not for a full ACS connection string, typically 170+ characters). The browser silently truncated the value to 128 characters before the form was ever submitted - the page reported "Email settings saved" as normal, with no indication anything was wrong, while a genuinely unusable, truncated key was what actually got stored. This is the same failure class the input-length items in section E already exist to catch, missed here because the truncation happens client-side, before any server-side check ever sees the full value. | Fixed: `maxlength=2000` (matching the server-side limit). New test asserts the rendered page carries this attribute (`test_the_connection_string_field_is_not_truncated_before_a_real_connection_string_fits`), so a future macro-default change cannot silently reintroduce this. |
