## Owner decisions applied (23 September 2026) — confirmed before any code was written

- **A scheduled run must work with nobody logged into Windows** (Addendum A 39.6, previously open, resolved by the owner). This is the single biggest design decision of the phase: it requires a genuinely headless entry point with no GUI dependency at all, and Windows Task Scheduler running the task under `LogonType=Password` (a real stored account/password), not the simpler "only when logged on" model.
- **A scheduled run processes every registered event**, one after another — not a per-event opt-in/opt-out.
- **Settings → Scheduling registers the real Windows Task Scheduler entry itself**, the moment the schedule is saved (via `schtasks.exe`), rather than waiting for the Phase 13 installer to do it — Phase 13 can take this over later without disturbing an already-configured schedule.
- **A missed occurrence (computer off/asleep) catches up as soon as the computer is next on** — Task Scheduler's own `StartWhenAvailable` setting.

## What was built

- **`services/singleinstance.py`** (closes the "single-instance lock" item carried forward since Phase 0/1, and BRD's own "unattended runs in Phase 12" note from Phase 5's F-32): an OS-level advisory file lock (`msvcrt.locking`), held for the life of the process and released automatically by Windows even on a crash — no stale-lock state possible. Both the interactive app (`main.py`) and the headless scheduled run take this same lock before touching the database, so at most one of the two ever runs at a time for a given data folder.
- **`services/scheduler.py`**: builds a Task Scheduler XML definition (weekly `CalendarTrigger` on the selected days/time — this computer's own local clock, matching how Task Scheduler itself works; `LogonType=Password`; `StartWhenAvailable=true`; `MultipleInstancesPolicy=IgnoreNew`) and registers/removes/queries it via `schtasks.exe`. The Windows account password is used only to pass to `schtasks /RP` at registration time — **never stored by this application anywhere**; Windows' own credential store (LSA secrets) retains it, exactly as if an administrator had typed it into the Task Scheduler UI by hand. `schtasks`' own stdout/stderr is never echoed into any log or message.
- **`ledsync/scheduled_run.py`** (the headless entry point Windows Task Scheduler invokes as `<python> -m ledsync.scheduled_run`): imports nothing from pywebview or the Flask web layer — confirmed by a dedicated test that a subprocess importing this module never loads `webview` into `sys.modules`, mirroring the same guarantee `main.py` already gave `ledsync.main`. Runs the exact same Download & Sync + notification pipeline the interactive Dashboard's own button uses (`services/downloads.run_job`, completely unchanged) for every registered event, one after another; one event's failure is caught and logged but never stops the rest. Brackets the whole multi-event run with its own `Scheduled Run` Started/Success/Failed/Blocked operational-log rows (BRD Section 25's operation vocabulary already reserved this name in Phase 9).
- **`services/settings.py`**: a new `schedule_username` field (not sensitive — just which Windows account the Task runs as, shown back on the page) alongside the existing enabled/days/time (Phase 10). The password is deliberately **not** a field here at all — it never reaches this module, or the database, in any form.
- **Settings → Scheduling page**: a Windows account field (auto-filled with the signed-in operator's own account) and a password field (required every time the schedule is saved while enabled — there is nothing to "keep unchanged" the way the ACS connection string works, since the password is never stored). A "Registered" / "Not registered" badge reflects the real, current Task Scheduler state (`schtasks /Query`), not just what this application's own database says.
- **Ordering that keeps the database and the real Task Scheduler entry from ever disagreeing**: `scheduler.register()`/`unregister()` is called *before* the settings are persisted. A bad account or password refuses the whole save — exactly like every other validation failure in this application — rather than leaving the saved settings claiming "enabled" while Windows disagrees. If the settings save itself then fails afterwards (a genuine database error, not a validation problem), the view makes a best-effort compensating `unregister()` call so Windows is not left with a task the database no longer claims (review fix, see below).
- **The Task always finds the venue's real data, regardless of which Windows account runs it**: the registering session's own application data folder is baked directly into the Task's `--data-dir` argument (review fix, see below) — a scheduled run never relies on the usual per-account `%LOCALAPPDATA%` resolution, which would otherwise silently point at an empty folder if the schedule is (sensibly) configured to run as a dedicated account different from whoever is signed in day to day.
- 23 new tests (`tests/test_phase12_scheduled.py`), plus a project-wide safety-net test fixture (`conftest.py`) that guarantees no test anywhere can shell out to the real `schtasks.exe` by accident.

## Live validation — DONE (owner, 23/09/26, on a real Entra ID-joined Windows 11 machine)

The owner registered and ran the real scheduled task end to end, using their own machine (`vatsanwork` local + `AzureAD\VatsanRamasubramania` Entra ID hybrid join). This surfaced three real, previously-unreachable issues — two genuine application bugs and one environmental/deployment prerequisite — none of which any prior automated test or code review could have caught, since all of them require Windows' actual Task Scheduler, credential store, and browser form rendering.

**1. Environmental prerequisite, not a code bug — Task Scheduler's stored-password logon needs the "Log on as a batch job" right.** The account first used (`vatsanwindows`, a local account) failed to launch at all (`Task Scheduler failed to log on ... Error Value: 2147943785` = `ERROR_LOGON_TYPE_NOT_GRANTED`) until that right was granted via `secpol.msc` → Local Policies → User Rights Assignment. This is standard Windows behaviour, not something `services/scheduler.py` can grant itself (`schtasks.exe /Create` does not request it). **Action for the venue runbook (Phase 13 installer/handover doc):** whichever account is chosen for the schedule must be granted "Log on as a batch job" before registering, and on a domain/Intune-managed machine this may require a Group Policy change rather than a local one.

**2. Environmental note — a scheduled account other than the interactive operator's own needs explicit NTFS access to the data folder.** Confirmed by testing with a scratch data folder nested inside the interactively-signed-in user's own profile (`...\AppData\Local\Temp\...`) and a *different* Windows account (`vatsanwindows`) running the Task: Windows' normal per-profile isolation blocked that account from the folder entirely until `icacls ... /grant` was run. This is expected Windows behaviour (Phase 12's own `--data-dir` bake-in, S-72, already correctly hands the scheduled process the right *path* — the operating system, not this application, still gates *access* to it). **Recommendation carried to Phase 13:** either register the schedule under the same account used interactively, or, if a dedicated unattended account is used, document/automate granting it access to the data folder.

**3. Two real application bugs found and fixed, root-causing Phase 11's long-open F-76/S-69** ("Notification failed: ... (Error)."):
   - `services/email_notify.py` `_send()` caught and re-mapped every exception without ever logging the original traceback anywhere (`raise _map_error(exc) from None` with no `log.exception` call) — unlike `notify()`'s own outer handler, which does log. This made the underlying cause permanently unrecoverable from the diagnostic log. **Fixed:** added `log.exception(...)` before the re-raise. This is what finally exposed the real exception: `binascii.Error: Incorrect padding` — whose class name is literally `Error`, explaining the previously-inexplicable `(Error)` in the message.
   - `services/settings.py` `validate_email_connection()` only checked the string's overall length (20–2000 characters) — it never actually parsed `endpoint=...;accesskey=...` or confirmed the access key was valid base64. A malformed connection string (most commonly caused by finding #4 below) was silently accepted at Save time and only failed, opaquely, the next time a notification was actually sent. **Fixed:** now parses the string the same way `email_notify._parse_connection_string` does and validates the key's base64 padding, refusing an invalid one immediately with a clear message.
   - `web/templates/settings_email.html`'s connection-string field used the `password_field` macro's default `maxlength="128"` — sized for the Cloud Storage access key (88 characters) but far too short for a full ACS connection string (`endpoint=https://...;accesskey=...`, typically 170+ characters). **The browser silently truncated every paste to 128 characters before the form was ever submitted** — two separate key rotations by the owner were each cut off mid-key at the exact same point, both appearing to "save successfully" in the UI while actually storing an unusable, truncated key. **Fixed:** `maxlength=2000` (matching the server-side limit), confirmed with a new page-content regression test.

**End-to-end result after all three fixes:** a real Task Scheduler-triggered run (account `vatsanwindows`, headless, no interactive session for that account) executed successfully — `Scheduled Run: Started → Success`, `Download & Sync: Identified 2, downloaded 1, synchronised 1, errors 0`, `Email Notification: Success` — all visible as real operational-log rows on the Dashboard/Logs pages of the same data folder the scheduled process wrote to.

**Not separately re-tested after the above fixes:** step 6 of the original checklist below (a full Windows *sign-out*, as opposed to a different, non-interactively-logged-in account executing the task) — the successful run above used a dedicated account that was never itself interactively signed in, which satisfies Addendum A 39.6's operational intent (the schedule does not depend on any interactive session), but a literal "sign out of the primary account entirely" pass was not separately repeated. Recorded as F-81 below; owner to confirm acceptance.

Original checklist, for reference (steps 1–5 and 7 completed as written above; step 6 as qualified above):
1. Open Settings → Scheduling in the real app.
2. Tick a day close to "now", set a time a few minutes ahead, confirm the Windows account shown is correct, and type that account's real password.
3. Save. The page should show "Registered" and a green confirmation.
4. Open Windows Task Scheduler (`taskschd.msc`) and confirm a task named **LEDAssetSync Scheduled Run** exists, is enabled, and its Triggers/Settings match what was configured (in particular: **General** tab shows "Run whether user is logged on or not").
5. Wait for the scheduled time (or right-click the task in Task Scheduler and choose **Run**) and confirm: the Dashboard shows the event(s) updated afterwards, and the Logs page shows a `Scheduled Run` row bracketing the per-event `Download & Sync` rows.
6. **The real "works with nobody logged in" guarantee**: sign out of Windows entirely (not just lock the screen) before the scheduled time, then sign back in afterwards and confirm the run still happened.
7. Turn scheduling off and confirm the Task Scheduler entry is removed.

## Independent Solution Architect review

**First pass: Rejected, pending one blocker** — reproduced and fixed same day (23/09/26):

- **Blocker:** the scheduled run resolved its data folder via `%LOCALAPPDATA%`, which is scoped to whichever Windows account actually runs the Task — not necessarily the account that registered it. Since Addendum A 39.6 exists precisely so a schedule can run as a dedicated account different from the interactively signed-in operator, the natural, sensible configuration (a separate service-style account) would have silently pointed the scheduled run at an *empty* data folder: no registered events found, `Scheduled Run` logged `Success` ("No events are registered; nothing to do") — forever, with no visible sign anything was wrong. **Fixed:** the registering session's own real `cfg.data_dir` is now baked directly into the Task's `--data-dir` argument at registration time, so a scheduled run always finds the venue's actual data regardless of which account Windows runs it as.
- **Fix now (1):** the disable path called `scheduler.unregister()` unguarded, unlike the enable path's `register()` — a `SchedulerError` there would have surfaced as a generic 500 page with no audit row, rather than a normal refused-save. Fixed: both paths are now guarded identically.
- **Fix now (2):** if `scheduler.register()` succeeded but the subsequent `cs.save_schedule()` database write then failed (a genuine SQLite error, not a validation problem), the real Task Scheduler entry could be left registered while the database still showed the old/no schedule — contradicting the "can never disagree" claim. Fixed: a database-save failure after a successful registration now makes a best-effort compensating `unregister()` call.

Confirmed sound and unchanged by the review: the Windows account password never leaks (traced end-to-end — form → `scheduler.register()` → the `/RP` subprocess argument only; confirmed it cannot reach the temp XML file, the database, a log line, or the page even on a failed save); the cross-process single-instance lock (`msvcrt.locking`) is correctly scoped, releases even on an exception, and has no TOCTOU gap; the headless entry point's import chain is genuinely free of any GUI/COM/desktop-session dependency; the Task Scheduler XML is structurally sound against the documented schema, with every operator/system-derived field correctly XML-escaped; the `_DEFAULT_RUNNER` test-isolation fix is correct and not needed anywhere else in the codebase. Fixes were verified by 4 new regression tests (1493 total) but were **not** put through a second independent review pass.
